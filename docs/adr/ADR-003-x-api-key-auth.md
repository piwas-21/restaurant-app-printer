# ADR-003 — X-Api-Key auth for printer-feed

**Status:** Accepted
**Date:** 2026-04-29

## Context

The printer-app polls the backend's order-event stream so it can print incoming orders to thermal printers. Until printer-app !1 / backend MR !20, the printer-app sent a long-lived Bearer JWT in the `Authorization` header — the same token shape used by browser clients.

Two problems with the JWT approach for a printer:

1. **No human in the loop to refresh.** A printer workstation is unattended and runs 24/7. Browser-style JWT lifetimes (minutes / hours) require a refresh-token flow that adds operational complexity for one specific consumer.
2. **JWTs encode user claims.** A printer is not a user. Issuing a JWT for the "printer user" overloads the auth model: every JWT-introspecting code path now has to special-case the printer principal (no email, no roles in the usual sense, custom audit identifier).

The printer-feed endpoint is a single, narrow surface: GET / SSE for new orders. It needs to be authenticated, but the authentication can be a long-lived per-installation secret rather than a session-bearing token.

## Decision

**The printer-feed endpoint authenticates with a long-lived per-installation API key sent in the `X-Api-Key` request header.** The bearer-JWT path is removed for this endpoint.

The API key is:
- Generated by the backend (admin UI or seeded), stored in the backend's persistence layer associated with a "printer client" record.
- Configured on the printer-app side via `PrinterConfiguration.ApiKey` (persisted in the local `config.json` next to other connection settings).
- Sent on every request to the printer-feed endpoint as `X-Api-Key: <key>`.
- Validated server-side by an `ApiKeyAuthFilter` that maps the key to the printer-client identity and authorises only the printer-feed routes.

## Consequences

### Positive
- **No expiry / refresh logic** on an unattended workstation.
- **Cleaner auth model on the backend** — JWT introspection paths don't carry a printer special-case.
- **Per-install rotation** — if one workstation's key leaks, rotate that one without touching others.
- **Header is greppable** — easy to audit traffic for printer-feed callers.

### Negative
- **Long-lived secret.** A leaked API key is valid forever (until manually rotated). JWTs at least expire.
- **Two parallel auth schemes** in the backend — Bearer JWT for users, X-Api-Key for printers. New endpoints must be explicit about which one applies.
- **`config.json` on disk holds the key in plaintext.** A workstation compromise yields the key.

### Mitigation for the negatives
- API keys are scoped to the printer-feed endpoint only via the filter — a leak doesn't grant access to user-shaped endpoints.
- Document a rotation runbook: the backend admin UI must support generating + revoking keys per printer. (Tracked in `docs/SPRINT-PLAN.md`.)
- For at-rest protection of `config.json`, future work can wrap it with the Windows Data Protection API (DPAPI) so the file is decryptable only by the workstation user account. Not in scope for the initial migration.

## Alternatives considered

### Alternative A: Keep the long-lived JWT
Solves nothing; same long-lived-secret tradeoff plus JWT introspection complexity.

### Alternative B: Mutual TLS (mTLS) with per-install certificates
Strongest auth on paper. But requires PKI bootstrap on every customer site (cert generation, CSR signing, distribution), and the backend ingress (typically behind a managed load balancer) needs mTLS termination support that not every hosted environment provides cheaply. Over-engineered for the threat model.

### Alternative C: Short-lived JWT issued via a refresh-token flow over the same X-Api-Key
This was considered — use the API key once at startup to mint a short-lived JWT, then send the JWT on subsequent requests. Adds round-trip complexity (one extra request per startup, plus refresh on expiry) for a security gain that's marginal given the printer is on a trusted LAN. Defer until / unless the threat model changes.
